# Encrypted offline web workspace — controlled development preview

GoreeCloud Tasks offers an **opt-in** encrypted offline draft vault in the web app's **Offline** view. It is **not a production multi-device offline-first engine** and does not replace the online API. No native offline queue exists yet.

## Encryption and trust boundary

- Non-extractable AES-256-GCM key derived in WebCrypto using PBKDF2-HMAC-SHA256 with 310,000 iterations, a random 16-byte per-vault salt, and a passphrase of at least 12 characters. A fresh 96-bit random GCM nonce protects every write.
- Additional authenticated data binds ciphertext to the browser origin. The only persistent record is the encrypted envelope in the IndexedDB database named goreecloud-tasks-offline-v1. This implementation never persists plaintext tasks/notes, API tokens, passphrases or encryption keys.
- Key and decrypted snapshot reside in memory only while the vault is unlocked. Lock, Disconnect and unmount clear the active session. Erase requires confirmation and deletes the local IndexedDB record, **not** server tasks or remote backups.
- An unlocked tab, hostile browser extension, keylogger, compromised web origin or weak passphrase can still compromise plaintext. This is at-rest encryption, not multi-factor authentication, a hardened key store, or protection against malicious running JavaScript.
- IndexedDB is per-origin and browser-profile, not bound to a verified GoreeCloud Identity subject. Use a trusted single-user browser. **Atomic IndexedDB compare-and-swap now detects stale writes between tabs**, using an authenticated, monotonic envelope revision plus a per-vault salt identity; a stale tab must lock/unlock to reload and cannot overwrite a newer draft queue or recreate an erased vault. Automatic cross-tab UI notifications/merges, per-user ACLs, identity-bound keys, key revocation and recovery remain unimplemented.
- Requires WebCrypto, HTTPS or localhost, and IndexedDB. First initialization requires a successful authenticated sync bootstrap. Each vault limits serialized data to 5,000,000 bytes, 5,000 tasks, 5,000 projects and 200 queued operations. Lost passphrases are unrecoverable and browsers may evict storage.

## Manual sync workflow

1. Log in with the development API token, which remains in memory. Open Offline, choose a passphrase and opt into encrypted storage. The client fetches a server bootstrap and saves an encrypted snapshot.
2. In an already-loaded browser tab, draft a standalone task with title/priority/optional due date/project, or queue a **title-only** edit for a cached task. The create draft receives a durable random idempotency key; the edit retains the original server expected_version.
3. Lock or close the tab. After reopening (when the app loads), unlock with the passphrase. Wrong passphrases or tampered ciphertext fail decryption.
4. When network access resumes, explicitly press **Sync now**. Create uses its original Idempotency-Key so an ambiguous network failure can be retried without duplicate task creation. Edit uses its original expected_version to prevent lost updates.
5. Each acknowledged write is removed from the encrypted queue. On HTTP 409, 404 or 410, sync **stops**, the conflicting operation is retained and marked CONFLICT; never silently overwrite server state. A network failure similarly preserves the queue. For a conflicting **title edit**, select **Compare with server** for an explicit authenticated GET and display the current server title/version beside the local title. Choose to discard the local draft, or after an additional confirmation **queue** the local title against that observed revision using a **new idempotency key**. This does not write until another deliberate **Sync now** action; any newer server revision still returns 409 and stops. If the task was deleted, the review only offers safe discard, not resurrection.
6. Once the queue is empty, the client refreshes a full bounded sync bootstrap. **Pull server changes** can later apply authenticated monotonic changefeed pages and deletion tombstones to the encrypted cache without re-downloading unchanged task records. It validates all pages in RAM, limits one pull to 10 pages of 200 events, and only saves after successful completion. Out-of-order, malformed or oversized pages abort without changing the stored snapshot. **Full snapshot refresh** remains an explicit fallback; both operations refuse to run while drafts are pending. Vault deletion requires user confirmation.

## Unsupported / next acceptance gates

- Only web task create and title edit drafts are supported; conflict review/re-queue applies only to existing-task title edits, not restored/deleted tasks or automatic field-level merge. Completion/reopen, deleting tasks, subtasks, projects, habits, attachments, recurring changes, and provider migration remain online-only.
- No service worker or offline app shell: **the app must already be loaded** to draft offline. Closing the tab can prevent reopening until connectivity returns, even though the encrypted snapshot persists.
- This now supports explicit, bounded incremental pulls and on-demand full bootstrap refresh, **not** a continuous multi-device changefeed replay/compaction engine. The vault's atomic revision compare-and-swap rejects conflicting writes by other tabs; it does not automatically notify the user of changes or merge concurrent unsynced drafts. Native Android/Linux encrypted offline editing, Identity-scoped keys, Mesh transport, GoreeShield retention, Wardveil security controls, full multi-tab lifecycle coordination/merging, background sync and production release/device acceptance remain pending.
- Cache erasure cannot delete unrelated devices, exports, backups or provider records. Use only with affirmative user consent and a trusted single-user browser. Do not interpret local synthetic tests as a real-world security audit.

## Synthetic cross-browser acceptance

Chromium, Firefox and WebKit acceptance fixtures check successful encrypted setup, ciphertext-only stored records, wrong-passphrase refusal, unlock/recovered queue, non-writing drafts, explicit replay, 409 conflict preservation without server overwrite, draft discard, monotonic incremental pulls, malformed-page rejection without local mutation, deletion tombstones and local vault erasure. A Chromium desktop scenario also opens two authenticated tabs and verifies stale-version writes fail without losing the newer tab's encrypted queue. Synthetic browser tests also compare a stale offline title against a simulated concurrent server edit and require an explicit decision to discard or separately queue a retry. The test harness blocks all external browser requests.
